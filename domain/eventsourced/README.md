# 事件溯源聚合的业务使用约束

聚合的状态必须能够仅由历史事件重建。推荐使用 `aggregate` tag、`New` 和 `ApplyXxx` 处理器；完整可执行用法见 [ExampleNew](example_test.go)，仓储装配见 [DDD / ES 速查](../../docs/reference/ddd-eventsourcing-quick-reference.md)。

## 构造与启动校验

每个应用持有一个 `MetadataRegistry`，在组合根通过 `RegisterSet(AggregateFromTag(&Account{}))` 或 Host 的模块聚合声明进行预检，检查成功后再接收业务请求。每个实例使用同一 registry 调用 `New[Account, ID]`；已有显式工厂可用 `InitAggregate`。

框架仅发现 `ApplyXxx` 方法，`ApplyEvent` / `ApplyAndRecord` 是框架保留入口。候选方法必须恰好接收一个实现 `domain.IDomainEvent` 的指针参数，不返回值或仅返回 `error`，不允许可变参数。同一 Go 事件类型只能有一个处理器；错误签名与重复处理器在注册阶段失败。`ValidateXxx`、`InspectXxx` 等辅助方法不参与路由。

处理器必须仅存在于 `*Aggregate` 的方法集中，不能同时存在于 `Aggregate` 的方法集中，避免值接收器修改副本后版本仍然推进。直接声明 `func (a *Aggregate) ApplyXxx(...)` 满足此要求；通过值嵌入提升的指针接收器方法也可使用。指针嵌入或接口嵌入会将方法同时提升到值方法集，因此需要在外层显式声明指针接收器转发方法，不能直接使用提升方法；被转发的嵌入指针或接口由聚合工厂初始化。

Metadata 内部字段不可由业务直接设置，通过扫描或 registry 构造后只读使用；禁止手造或覆盖 Metadata。类型样本允许 `(*Account)(nil)`，实际绑定的实例和实际应用的事件必须非 nil。回放工厂只构造空聚合，业务初始值通过事件产生。

## 命令与回放

| 入口 | 使用方 | 契约 |
| --- | --- | --- |
| `Deposit` 等业务命令 | Application | 先完成业务校验，再通过 `ApplyAndRecord` 应用并记录事件 |
| `ApplyXxx` | 框架分发器 | 使用指针 receiver，仅根据当前状态和事件更新内存字段 |
| `ApplyEvent` | 仓储回放 | 按事件顺序应用，成功后递增版本，不记录未提交事件，不去重 |
| `RecordUncommittedEvent` | 自定义聚合实现 | 仅记录事件，不更新状态与版本；常规命令使用 `ApplyAndRecord` |

业务字段尽量不导出，通过只读方法查询；Application 不直接调用 `ApplyXxx`、`ApplyEvent` 或手改版本。时间、随机数、外部查询结果在命令阶段取得并写入事件，处理器不能重新读取这些值，也不能发送消息或操作数据库。

事件应用后不可修改事件及其引用数据。聚合实例不可并发使用。任何应用错误（包括 handler panic 转换的错误）都要求丢弃实例并重新加载：版本和待提交列表不会推进，但 handler 可能已经修改业务字段，框架不回滚这些字段。

## 业务验收

新增聚合或事件时，业务包的测试至少验证：

1. 所有聚合声明能通过启动预检；为每种事件准备实际应用场景，避免未声明处理器直到线上才暴露。
2. 非法命令返回错误后，业务状态、版本和未提交事件列表均不变。
3. 从空聚合执行命令，取出产生的事件，向另一个空聚合逐条回放；业务状态与版本一致，回放实例没有未提交事件。业务状态要单独比较，不比较含绑定对象的整个基类。
4. 需要读取的历史事件版本仍能重建状态；涉及快照时验证“快照 + 后续事件”与完整回放一致。

签名预检无法证明处理器的确定性，也无法阻止直接调用导出的 Go 方法；这些约束由业务测试和评审落实。处理器是否覆盖全部历史事件，同样需要实际回放测试验证。
